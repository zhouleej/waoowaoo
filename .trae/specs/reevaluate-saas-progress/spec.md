# SaaS 版本开发进展重新评估 Spec

## Why
本地历史 spec 已不再反映当前代码库状态，需要清空旧规划并基于现有实现重新评估 SaaS 版本进展。该评估用于明确当前完成度、未完成缺口、上线风险和下一阶段开发优先级。

## What Changes
- 清除本地 `.trae/specs` 下旧有 SaaS 与平台管理相关 spec，避免后续执行误用过期任务。
- 基于当前代码库重新梳理 SaaS 版本的已完成能力、进行中能力、缺口与风险。
- 形成新的评估型 spec，作为后续 SaaS 版本继续规划、任务拆解和验收的唯一基础。
- 明确下一阶段应优先补齐租户上下文、资源隔离、订阅支付闭环、权益执行、企业自助门户和测试保障。

## Impact
- Affected specs: SaaS 版本进展评估、SaaS 平台化规划、企业组织管理、平台管理后台、计费订阅能力。
- Affected code: `prisma/schema.prisma`、`src/lib/saas/*`、`src/lib/billing/*`、`src/lib/platform-admin.ts`、`src/app/api/platform/*`、`src/app/api/organizations/*`、`src/app/[locale]/admin/platform/*`、`src/app/[locale]/admin/organizations/*`。

## ADDED Requirements

### Requirement: 本地 Spec 基线重置
系统 SHALL 清除本地旧 spec，并建立新的 SaaS 版本进展评估 spec 作为后续规划基础。

#### Scenario: 旧 Spec 已清除
- **WHEN** 开发者查看 `.trae/specs` 目录
- **THEN** 不应再看到旧的 `platform-admin-*`、`saas-*`、`upgrade-saas-platform` 等过期 spec 目录

#### Scenario: 新评估 Spec 可用
- **WHEN** 开发者需要继续 SaaS 版本规划
- **THEN** 可从新的 `reevaluate-saas-progress` spec 中获得当前状态、缺口、风险和下一阶段方向

### Requirement: SaaS 当前进展评估
系统 SHALL 以当前代码库为准，评估 SaaS 版本的实际开发进展，而不是沿用历史计划描述。

#### Scenario: 识别已完成能力
- **WHEN** 评估 SaaS 版本现状
- **THEN** 应识别已具备的多租户组织、成员角色、平台管理员、套餐权益、订阅、订单、发票、余额、用量、审计日志等基础结构

#### Scenario: 识别接口和 UI 状态
- **WHEN** 评估 SaaS 版本现状
- **THEN** 应识别平台管理接口和后台 UI 已基本成型，企业端组织与账单能力已有入口但仍未形成完整客户自助门户

#### Scenario: 识别数据库状态
- **WHEN** 评估 SaaS 版本现状
- **THEN** 应同时记录模型定义状态与本地数据库实际初始化状态，避免将 schema 中存在的模型误判为运行环境已可用

### Requirement: SaaS 缺口和风险评估
系统 SHALL 明确 SaaS 版本距离完整商业化闭环仍存在的关键缺口和上线风险。

#### Scenario: 识别商业闭环缺口
- **WHEN** 评估订阅计费能力
- **THEN** 应指出订单、订阅、发票模型和后台管理能力已存在，但支付回调、自动续费、退款、对账、到期、欠费、降级等闭环能力仍不完整

#### Scenario: 识别租户隔离风险
- **WHEN** 评估多租户安全性
- **THEN** 应指出项目、任务、资产、文件、运行记录等业务资源需要逐接口确认组织隔离，避免跨租户访问风险

#### Scenario: 识别权益执行风险
- **WHEN** 评估套餐权益能力
- **THEN** 应指出权益数据已具备基础执行入口，但仍需强类型 schema、统一校验入口和覆盖更多权益项

### Requirement: 下一阶段优先级定义
系统 SHALL 给出下一阶段 SaaS 版本建设的优先级，以指导后续 `/plan` 和 `/tasks`。

#### Scenario: 确定开发主线
- **WHEN** 团队继续规划 SaaS 版本
- **THEN** 应优先围绕显式组织上下文、业务资源租户隔离、订阅支付状态机、统一权益执行、企业自助门户、测试与审计保障展开

#### Scenario: 确定上线门槛
- **WHEN** 团队判断 SaaS 版本是否可上线
- **THEN** 应要求权限隔离、计费一致性、订阅状态机、支付回调幂等、高危操作审计等验证全部通过

## MODIFIED Requirements

### Requirement: SaaS 版本状态描述
SaaS 版本状态 SHALL 从“历史计划驱动”调整为“当前代码事实驱动”。当前版本应定义为“SaaS 管理底座与计费接入原型完成，待补齐租户上下文、支付订阅闭环、权益强校验和企业自助门户”，不应描述为完整 SaaS 商业化闭环已完成。

### Requirement: 平台管理能力定位
平台管理能力 SHALL 被定位为当前较成熟的后台运维能力，包含企业、用户、套餐、订阅、订单、发票、配置、统计、审计等管理入口；但这些后台能力不能替代企业客户自助购买、续费、充值、开票和配额管理能力。

### Requirement: 数据库完成度判定
数据库完成度 SHALL 同时区分 schema 建模完成与本地运行库初始化完成。若本地数据库缺少 SaaS 计费相关表，则界面和接口应视为运行环境未完整就绪。

## REMOVED Requirements

### Requirement: 沿用旧 Spec 继续开发
**Reason**: 旧 spec 与当前代码库状态存在偏差，继续沿用会造成任务重复、优先级混乱和验收依据不准确。
**Migration**: 已清除本地旧 spec，后续以 `reevaluate-saas-progress` 为新的 SaaS 版本规划入口。

## Current Assessment

### 已完成或基本完成
- SaaS 数据模型骨架已建立，包括组织、成员、余额、用量、套餐、权益、订阅、订单、发票、邀请、企业审计、平台审计和系统配置。
- 平台管理员体系已建立，用户具备平台管理员和全局锁定字段，登录态会透传管理员状态。
- 平台管理员鉴权已支持数据库字段和环境变量双通道校验，并提供统一未授权响应。
- 企业组织基础能力已具备，普通用户可创建组织并成为 owner，系统可维护组织余额和成员关系。
- 企业角色权限已有基础封装，可按 owner、admin、member 校验组织和成员状态。
- 套餐权益和企业消费前校验已有初步入口，可按任务类型、月度额度、成员配额和企业余额判断消费可行性。
- 任务计费流程已开始接入企业组织维度，可记录组织用量并扣减组织余额中的余额部分。
- 平台侧管理接口和后台 UI 已覆盖企业、用户、套餐、订阅、订单、发票、配置、统计和审计等核心管理场景。
- 企业端已有组织列表、创建组织和组织详情相关入口，具备客户门户雏形。

### 未完成或需要强化
- 缺少显式当前组织选择、切换和请求上下文传递机制，当前自动取第一个活跃组织不足以支撑成熟多组织用户场景。
- 项目、任务、资产、文件、运行记录等业务资源尚需逐接口确认是否强制写入和过滤 `organizationId`。
- 订单、订阅和发票更多停留在后台管理对象，缺少用户自助购买、升级、续费、充值、退款、对账和支付回调闭环。
- 订阅状态机不完整，自动续期、到期处理、欠费处理、降级和业务状态同步仍需补齐。
- 套餐权益以 JSON 形式存储，缺少强类型定义、统一校验入口和面向 seats、并发、存储、模型权限、API 调用量、功能开关等扩展权益的统一执行。
- 成员配额与月度用量已可累计，但缺少明确周期重置、历史账期归档和运营报表机制。
- 企业自助 UI 仍弱于平台后台，需要补齐套餐选择、订阅状态、余额充值、订单支付、发票申请、成员配额、用量趋势和企业审计等用户可操作界面。
- 测试保障不足，缺少系统性的租户隔离、计费一致性、订阅状态机、支付回调幂等和高危操作审计验证。

### 主要风险
- 跨租户访问风险：资源接口若未强制组织过滤，可能导致企业间数据泄露。
- 计费一致性风险：企业余额与用户余额计费并存，如果幂等、回滚和并发扣减未统一，可能导致重复扣费或漏扣。
- 权益理解不一致风险：权益 key 分散且缺少强类型约束，前后端和运营配置容易出现语义偏差。
- 订阅状态失真风险：自动续期、到期、欠费和降级机制缺失会导致企业业务状态与真实付费状态不一致。
- 运营权限风险：平台管理员权限较高，需要明确最小权限、变更流程和审计覆盖。
- 产品完整性风险：平台后台能力领先于客户自助能力，不足以支撑对外 SaaS 商业化发布。

## Next Priority
- 第一优先级：建立显式当前组织上下文，并完成项目、任务、资产、文件、运行记录等核心资源的租户隔离审计与修复。
- 第二优先级：补齐订阅支付闭环，包括订单支付、支付回调幂等、自动续费、到期、欠费、降级、退款和对账。
- 第三优先级：建立强类型套餐权益 schema 和统一执行入口，覆盖席位、并发、存储、模型、API 调用量、功能开关和超额策略。
- 第四优先级：完善企业自助门户，覆盖套餐订阅、余额充值、用量趋势、成员配额、订单发票和审计记录。
- 第五优先级：补齐 SaaS 上线前验证体系，覆盖权限隔离、计费一致性、订阅状态机、支付回调幂等和高危操作审计。
